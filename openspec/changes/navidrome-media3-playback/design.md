# Design: Navidrome Media3 Playback

## Dependency direction

Playback follows the existing package-level dependency direction:

    presentation -> domain <- data / Media3 adapter

No DI framework, database, additional Gradle module or provider-neutral
playback abstraction is introduced.

## Package direction

The expected package is:

    features/playback/
      domain/
      data/
      presentation/

AndroidX Media3 types remain behind the playback adapter boundary.

`MainActivity` remains the explicit composition root for #1.

Issue #15 may later move player ownership into a Media3 service without
requiring library screens to understand Media3 internals.

## Dependency selection

The first implementation pins AndroidX Media3 1.11.1.

Required modules:

- `androidx.media3:media3-exoplayer`
- `androidx.media3:media3-datasource-okhttp`

No Media3 UI or session dependency is required for #1.

Compose owns the visible controls.

The OkHttp Media3 data source allows playback to preserve the application's
existing network policy rather than introducing a separate HTTP stack.

## Selected-track model

Playback receives a small safe model containing:

- opaque track id;
- title;
- optional artist.

It MUST NOT contain:

- a resolved stream URL;
- server endpoint;
- username;
- password;
- authentication token;
- authentication salt.

The selected playback model may be mapped from `AlbumTrack` at the
presentation/application boundary.

The library domain does not gain playback-specific transport state.

## Account ownership

`ServerAccountIdentity` remains the canonical account key.

A play request includes the exact current account and opaque track id.

Before resolving a stream, the playback data boundary MUST:

1. read credentials for the account endpoint from `AuthSecretStore`;
2. reject missing credentials;
3. reject a stored username different from the account identity;
4. create a fresh OpenSubsonic authentication signature;
5. resolve the stream request only for that account and track.

When the current authenticated identity changes, active playback MUST stop and
its media item MUST be cleared before another account can play.

No account-specific playback state is persisted in #1.

## Authenticated stream request

The OpenSubsonic stream endpoint is resolved only when playback starts.

The request includes the opaque track id and standard OpenSubsonic
authentication parameters generated by the existing signer.

The resolved request is an internal implementation detail.

It MUST NOT be:

- exposed through domain state;
- exposed through Compose state;
- stored in saved state;
- persisted to DataStore;
- printed through `toString`;
- logged on playback failure.

An internal resolved-source wrapper should redact its string representation.

## Redirect policy

Authenticated media requests MUST NOT follow redirects.

The Media3 `OkHttpDataSource` will use an application-controlled OkHttpClient
with both ordinary and SSL redirects disabled.

This preserves the security invariant already established for authenticated
OpenSubsonic requests.

## Media3 player boundary

The concrete Android adapter owns an ExoPlayer instance.

For a selected track it will:

1. resolve the secure stream request;
2. create the Media3 media item/source in memory;
3. prepare the player;
4. begin playback;
5. map player callbacks into transport-independent playback state.

Supported commands for #1:

- play selected track;
- pause;
- resume;
- stop;
- release.

`stop` and `release` MUST clear the active Media3 item so its signed request is
not retained longer than necessary.

## Playback state

Presentation-facing state remains framework independent.

The minimum phases are:

- idle;
- preparing;
- playing;
- paused;
- stopped;
- error.

Safe state may include selected track title and artist.

Error state contains a safe category/message only.

Raw `PlaybackException`, request URI, response body and exception message MUST
NOT enter presentation state.

Terminal failures MUST transition away from `playing`.

## Recoverable failures

The minimum safe failure categories are expected to distinguish:

- authentication required;
- network/media-source failure;
- unsupported playback/decoder;
- unknown playback failure.

Presentation offers retry by issuing a new play request, which also creates a
fresh authentication signature.

## FLAC behavior

Media3/ExoPlayer supports FLAC containers.

The application minSdk remains API 23.

A platform FLAC decoder is guaranteed by Android from API 27; earlier Android
versions may depend on device codec support unless a bundled software decoder
is added.

#1 does not add a native decoder extension solely to cover every older device.

An unsupported decoder therefore maps to a recoverable playback error rather
than leaving the UI falsely playing.

## Lifecycle

For #1 the player is application-feature state, not a background service.

The playback ViewModel/controller boundary must survive normal Compose
recomposition without creating duplicate players.

Player creation should occur lazily through the ViewModel factory or another
single-owner construction path so an Activity recreation does not eagerly
create an unused second player.

The owner releases the player when the playback ViewModel is permanently
cleared.

Background playback and Android system lifecycle ownership remain #15.

## Testing

JVM tests should cover:

- exact-account credential lookup;
- username mismatch rejection;
- fresh signing per play;
- stream-request construction without persistence;
- redacted resolved-source string representation;
- no redirect-capable playback HTTP client;
- safe state transitions;
- terminal error never remaining `playing`;
- pause/resume/stop behavior through a fake playback engine;
- account change causing playback cleanup.

Media3 Android integration is validated by build/runtime evidence rather than
pretending the JVM fake proves ExoPlayer itself.

Final device validation must record only pass/fail and safe characteristics.

## Privacy

No verification artifact may contain:

- personal Navidrome endpoints;
- personal usernames;
- passwords;
- tokens or salts;
- resolved stream URLs;
- personal media metadata.

Synthetic fixture metadata from issue #35 may be used where automated
integration coverage is useful.
